# API conventions

What holds across every endpoint. The reference pages that follow do not repeat any of
it.

## Base URL

Everything is relative to `APP_URL` — the public address, which is also the OIDC issuer.
The two must match exactly, character for character.

## Authentication

Three schemes. They are not interchangeable, and conflating them is the most common
integration mistake:

| Scheme | Carried as | Issued by | Used by |
|---|---|---|---|
| Session token | `Authorization: Bearer` | `POST /api/auth/login`, `POST /api/actors/authenticate` | every `/api/*` business endpoint |
| OIDC access token | `Authorization: Bearer` | `POST /api/oidc/token` | `GET /api/oidc/userinfo` only |
| Browser session | `soulauth_session` cookie | the login flow | `GET /api/oidc/authorize` |

Two consequences worth stating:

- **A session token is not an OIDC access token.** They are both bearer tokens on the
  same `Authorization: Bearer` header, so sending the wrong one gets you a 401 that looks
  like an expired credential.
- **Cookies do not authenticate the API.** They serve the browser and OIDC flows. An
  API call with only a cookie is unauthenticated.

Each endpoint below states which scheme it takes, or that it is public.

## Errors

One shape, everywhere:

```json
{
  "error": "missing_permission",
  "message": "Missing permission: soulauth:roles.read",
  "required_permission": "soulauth:roles.read"
}
```

- `error` is a **stable machine-readable code**. Branch on it.
- `message` is for humans. Its wording can change in any release; it is not part of the
  contract.
- Some errors carry documented extra fields — `required_permission` on
  `missing_permission`, `locked_until_seconds` on `account_locked`. They are additive.

<Status kind="tested" guard="conformance::j6" /> guards that no endpoint returns a
different shape — including the failure mode this replaced, where a handful of endpoints
answered with a bare status code and an **empty body**, leaving a client with no code and
no message to work from.

### The one exception

OIDC protocol endpoints use the shape RFC 6749 §5.2 mandates:

```json
{ "error": "invalid_grant", "error_description": "Refresh token already used" }
```

This is not an inconsistency to fix — the specification requires it.

## Status codes

| | |
|---|---|
| `200` | Success |
| `204` | Success, no body (role and permission assignment) |
| `400` | Malformed request or failed validation |
| `401` | Missing, malformed or rejected credentials |
| `403` | Authenticated, but not permitted — or the wrong subject type for this endpoint |
| `404` | Not found; also returned instead of `403` where existence itself is sensitive |
| `409` | Conflict (email or username already taken) |
| `429` | Rate limited, or the account/IP is locked out |
| `501` | The route exists but this deployment has not configured the feature |
| `503` | A dependency was briefly unavailable — the request was **not** processed |

`501` rather than `404`: a federated login endpoint on a deployment with no OAuth
credentials configured is not "not found" — the route is there, the semantics are defined, the
operator simply has not filled in the settings. A `404` would send them looking for the
wrong problem.

`503` matters for retry logic: it says the request never ran, so retrying it is safe.
That is the opposite of `429`, where the request was rejected on purpose and retrying
immediately makes things worse. Branch on the two separately.

## Identifiers

Record identifiers appear as `table:key`, for example `actor_identity:lnhl…`. Where a
path takes one, both the prefixed and bare forms are accepted — a colon inside a URL
gets percent-encoded by many client libraries, and the two forms mean the same thing.

::: warning A resource ID is not a subject
`ActorIdentity` has both a record ID and a `subject_key`. They are different namespaces.
Do not treat one as the other, and do not assume an implementation keeps them equal.
:::

## Pagination

List endpoints that support it take `limit` and `offset`. Responses are bare arrays or
bare objects — there is no envelope, no `data` wrapper.

## Rate limiting and lockout

Per-IP rate limits and per-account lockout both apply to authentication endpoints. Both
are stored in the database, so they are shared across replicas rather than per-process.
Exceeding either returns `429`; the lockout response carries `locked_until_seconds`.
